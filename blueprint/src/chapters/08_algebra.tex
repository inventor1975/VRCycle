\section{Position}
\label{sec:algebra_position}

VR-Algebra is the eighth work of the cycle.  It applies the VR-Apparatus
framework (Chapter~\ref{chap:apparatus}) to the standard algebraic
hierarchy: additive groups, rings, multiplicative groups, fields, and
modules.  Five operational typeclasses are constructed as layers over
the corresponding mathlib structures.

\textbf{Load-bearing finding.} Finding~A3 (apparatus reuse confirmed):
the \texttt{PredicateOperationality} apparatus extends to all five
algebraic structures \emph{without modification}.  For modules
(\texttt{OperationalModule}), the predicate on the carrier type~$M$
is exactly the one registered in v0.1.0 for additive groups;
no new \texttt{PredicateOperationality} instance is needed.
This is not ``extends naturally'' in a loose sense but literally
``uses the v0.1.0 instance unchanged''.
Finding~A3 is the empirical confirmation that VR-Apparatus is a
genuine methodological framework, not a single-use solution for
Hahn-Banach.

\textbf{Publication note.} VR-Algebra is the only chapter of the cycle
without a companion Lean Software record on Zenodo.  The Lean code is
cited by GitHub tag \texttt{v1.12-vr-operational-algebra-v1.0.0},
commit \texttt{5e8f8e0}.  This is a deliberate workflow simplification
without compromising reproducibility.

64 public objects, 3\,977 lines.
\noindent\axiomprofile{[]}: most typeclass definitions, Mode~A theorems,
subgroup theorems, Mode~B main theorem.
\noindent\axiomprofile{[propext]}: $\mathbb{Z}$ instances and demonstrations.
\noindent\axiomprofile{[propext, Quot.sound]}: $\mathbb{Z}/n\mathbb{Z}$
instances and \texttt{OperationalField} typeclass.
\noindent\axiomprofile{[propext, Classical.choice, Quot.sound]}: $\mathbb{Q}$
instances, \texttt{inv\_isModeAOp\_field}, \texttt{toOperationalGroupUnits}.

\section{Mode~B audit: image of operational subgroup}

\begin{definition}[Operational subgroup predicate]
\label{def:IsOperationalAddSubgroup}
\lean{VR.Algebra.IsOperationalAddSubgroup,
      VR.Algebra.bot_isOperationalAddSubgroup,
      VR.Algebra.top_isOperationalAddSubgroup,
      VR.Algebra.inf_isOperationalAddSubgroup}
\leanok
\uses{def:OperationalAddGroup}
$\texttt{IsOperationalAddSubgroup}\,H := \forall x \in H,\;
\texttt{IsOperational}\,x$.  A subgroup is operational when all its
elements are operational.
Closure: $\bot$ is always operational; $\top$ is operational when
all elements are; $H \sqcap K$ inherits from $H$.
All at \axiomprofile{[]}.
\end{definition}

\begin{theorem}[Substantive Mode~B audit: image is operational]
\label{thm:image_modeB}
\lean{VR.Algebra.image_isOperationalAddSubgroup_isModeBOp}
\leanok
\uses{def:IsOperationalAddSubgroup, def:IsModeBOp}
The image of an operational subgroup under an operational group homomorphism
is an operational subgroup.  Formally:
$\texttt{image\_isOperationalAddSubgroup\_isModeBOp}$:
\texttt{IsModeBOp} with $PA = \texttt{IsOperationalAddSubgroup}$,
$PB = \texttt{IsOperationalAddSubgroup}$, $W = \text{morphism-operational}$,
$f = \phi(\text{image})$.

Proof: \texttt{obtain} $\langle x, hxS, \texttt{rfl}\rangle$ from
$\texttt{AddSubgroup.mem\_map}$; \texttt{exact hW x (hS x hxS)}.
This is one tactic step after the constructive existential is extracted.
\axiomprofile{[]}.  \texttt{Classical.choice} absent: \texttt{AddSubgroup.mem\_map}
is constructive (no classical reasoning in the membership proof).
\end{theorem}

\subsection*{Structural contrast with VR-Audit Mode~B}

\begin{remark}[Algebraic vs analytic Mode~B]
\label{rem:modeB_contrast}
\leanok
\uses{thm:image_modeB, thm:HahnBanachOperational_Hilbert}
VR-Audit (Chapter~\ref{chap:audit}) Mode~B audit (Hahn-Banach): six
proof steps, Riesz representation, orthogonal projection, locatedness
condition, classical choice via \texttt{toDual}.

VR-Algebra Mode~B audit: one tactic step after destructuring.
\texttt{AddSubgroup.mem\_map} delivers a constructive existential;
no choice, no limits, no classical machinery.

Both are legitimate Mode~B instances.  The contrast demonstrates the
\emph{spectrum} of Mode~B: the algebraic case is mechanically extractable
from constructive witnesses built into mathlib's algebraic API (Finding~A11);
the analytic case requires substantial infrastructure because the witness
involves a classical object (Riesz vector) connected to the result via
a non-trivial factorisation.
\end{remark}

\begin{remark}[Finding~A15 --- Import-context ceiling escalation]
\label{rem:A15}
\lean{VR.Algebra.inv_isModeAOp_field}
\leanok
\uses{thm:field_modeA}
$\texttt{inv\_isModeAOp\_field}$ for generic \texttt{[OperationalField K]}:
\axiomprofile{[propext, Classical.choice, Quot.sound]}.
But $\texttt{instPredOpField}$ (same \texttt{[OperationalField K]} assumption,
no $({\cdot}^{-1})$ in the type): \axiomprofile{[propext, Quot.sound]}.

Root cause: the apparatus import chain imports
\texttt{Mathlib.Data.Real.Basic} (via
\texttt{VRCycle.Apparatus.ModeA} $\to$ \texttt{VRCycle.Audit.Computable}),
which introduces $\mathbb{R}$ instances that affect how Lean resolves
\texttt{Inv K} for generic \texttt{[Field K]} when $({\cdot}^{-1})$
appears in the \texttt{IsModeAOp} type.
This is an import-context effect, not a logical property of
\texttt{inv\_isOperational}.  The logical ceiling remains
\texttt{[propext, Quot.sound]}.
\end{remark}

\begin{remark}[Finding~A16 --- Structural confirmation]
\label{rem:A16}
\lean{VR.Algebra.OperationalField.toOperationalGroupUnits}
\leanok
\uses{def:OperationalField}
$\texttt{OperationalField.toOperationalGroupUnits}$:
\axiomprofile{[propext, Classical.choice, Quot.sound]}.
Systematic isolation attempts (v0.4.0 Stage~2) confirm two distinct
root causes:

(1)~\texttt{inv\_isModeAOp\_field}: apparatus import chain (described
in A15).  Even a minimal-import file without \texttt{Instances.lean}
shows \texttt{Classical.choice}.

(2)~\texttt{toOperationalGroupUnits}: proof-structural.  Any valid proof
must use \texttt{Units.val\_inv\_eq\_inv\_val} to connect
$(u^{-1} : K^\times).\texttt{val}$ to $(u.\texttt{val})^{-1}$.
After this rewrite, the goal contains field-level $(u : K)^{-1}$,
which inherits \texttt{Classical.choice}.  No alternative path exists.

These two objects are the only non-eliminable sources of
\texttt{Classical.choice} in the algebraic hierarchy.  They are
structural consequences of field inversion, not violations of
operational discipline.
\end{remark}

\section{Recognition discipline: bidirectional signature}
\label{sec:algebra_recognition}

\begin{remark}[Removal and introduction as partner operations]
\label{rem:recognition_bidirectional}
\lean{VR.Algebra.OperationalGroup}
\leanok
\uses{def:OperationalGroup}
Prior cycle works (Apparatus scope limitations) showed recognition
discipline predominantly as \emph{removal} (three planned abstractions
dropped).  VR-Algebra adds the partner operation: \emph{introduction}
when justified.

\textbf{Removal examples}: \texttt{OperationalCommRing} omitted twice
(Finding~A0, A9 --- no natural instances or immediate diamond); bundled
\texttt{OperationalSubgroup} typeclass dropped (Finding~A6 --- predicate
suffices); \texttt{one\_isOperational\_bridge} omitted (already a field);
\texttt{mul\_chain\_isOperational} omitted (derivable by compose).

\textbf{Introduction example}: \texttt{OperationalGroup} (Finding~A0
removed it in v0.1.0; Finding~A12 introduced it in v0.3.0 when the
first concrete instance arrived --- $\mathbb{Q}^\times$ via
\texttt{OperationalField.toOperationalGroupUnits}).

The bidirectional pattern --- remove preemptive abstractions AND
introduce justified abstractions when users arrive --- is the complete
recognition discipline signature, anticipated in VR-Apparatus and now
confirmed by VR-Algebra.
\end{remark}

naturally distinguishes internal from external operations.
\end{finding}

\section{Position relative to the Apparatus framework}

\begin{remark}[Algebra confirms Apparatus generality]
\label{rem:algebra_confirms_apparatus}
Chapter~\ref{chap:apparatus} (VR-Apparatus) formalised the methodological
framework; Chapter~\ref{chap:audit} (VR-Audit) applied it to Hahn-Banach
in functional analysis.  One application could be coincidental.

VR-Algebra provides the second application on entirely different territory
(algebraic structures rather than functional analysis) and explicitly
confirms that the apparatus requires no modification.  The key confirmation
is Finding~A3: four independent apparatus registrations across four versions
of the algebraic hierarchy, with the fourth (modules) requiring no new
registration at all.

Without VR-Algebra, VR-Apparatus would be a framework with one well-studied
application.  With VR-Algebra, it is a framework demonstrated to be
territory-independent.
\end{remark}
